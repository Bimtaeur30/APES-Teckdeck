# AI 협업 가이드

## 1. 가장 먼저 할 일

1. 코드, 에셋 또는 설정을 변경하기 전에 사용자의 이름이나 이니셜을 확인한다.
2. 현재 대화에서 이름이나 이니셜을 확실히 알 수 없다면 반드시 사용자에게 질문하고 답을 기다린다.
3. `Assets/_MemeberWorkspace/<사용자 이름 또는 이니셜>/` 폴더를 찾는다.
4. 해당 사용자 폴더가 없으면 이름을 다시 확인한 뒤 그 폴더를 생성한다. 추측한 이름으로 만들지 않는다.
5. 사용자 폴더의 `_AgentLog/PROGRESS.md`와 `_AgentLog/phases/`를 먼저 읽어 기존 진행도와 다음 작업을 파악한다.
6. 기록 폴더나 파일이 없다면 `Assets/_MemeberWorkspace/_Templates/`의 양식을 복사해 생성한다.

## 2. 절대적인 작업영역 제한

- 기능 구현 중에는 확인된 `Assets/_MemeberWorkspace/<사용자>/` 내부만 생성·수정·이동·삭제할 수 있다.
- 다른 사용자의 폴더는 읽거나 수정하지 않는다. 협업상 반드시 확인해야 한다면 먼저 사용자 승인을 받는다.
- `Assets`, `Packages`, `ProjectSettings`, 씬, 프리팹 등 공용 경로를 직접 수정하지 않는다.
- 공용 파일 변경이 필요하면 필요한 이유, 대상 파일, 예상 변경 내용을 설명하고 사용자에게 별도 승인을 요청한다.
- 승인받은 공용 변경은 사용자가 명확히 지정한 범위에만 적용한다.
- 자동 생성 파일, 캐시, IDE 설정 및 요청과 무관한 파일은 건드리지 않는다.
- 이 가이드와 `Assets/_MemeberWorkspace/_Templates/`는 프로젝트 관리자용 공용 파일이다. 일반 기능 작업 중에는 수정하지 않는다.

## 3. Phase 승인 절차

모든 구현 요청은 다음 순서를 지킨다.

1. 요구사항을 자신의 말로 짧게 재확인한다.
2. 현재 코드와 진행 기록을 읽기 전용으로 조사한다.
3. 작업을 검토 가능한 크기의 Phase로 나눈다.
4. 각 Phase에 목표, 변경 예정 파일, 구현 방법, 검증 방법, 범위 밖 항목을 적는다.
5. 계획을 사용자에게 제시하고 명시적인 승인을 기다린다.
6. 승인 후 Phase를 순서대로 하나씩 구현한다.
7. 요구 의도를 넘어서는 기능, 리팩터링, 패키지 변경 또는 편의 기능은 임의로 추가하지 않는다.
8. 진행 중 계획 변경이 필요하면 구현을 멈추고 변경 이유와 새 계획을 승인받는다.

단순 설명이나 읽기 전용 조사에는 승인이 필요하지 않다. 파일을 변경하는 순간부터 위 절차가 적용된다.

## 4. 프로젝트 기술 기준

- 비동기 처리는 Cysharp의 `UniTask`를 우선 사용한다.
- 트윈, 시간 기반 연출, UI·오브젝트 애니메이션은 `DOTween`을 우선 사용한다.
- 기존 코드 구조와 Unity 버전에서 해당 API를 사용할 수 있는지 먼저 확인한다.
- 반환값이 없는 비동기 작업도 가능한 한 `UniTask`를 반환한다. Unity 이벤트처럼 반환형을 바꿀 수 없는 진입점에서만 `UniTaskVoid`를 제한적으로 사용하고 예외를 관찰한다.
- `CancellationToken`을 전달하고, 가능한 경우 `GetCancellationTokenOnDestroy()`와 연결해 오브젝트 파괴나 씬 전환 뒤 비동기 작업이 남지 않도록 한다.
- UniTask 패키지가 없거나 버전 변경이 필요하면 임의로 설치·변경하지 않고 사용자에게 별도 승인을 받는다.
- DOTween Sequence와 Tween의 소유자, 종료 조건, Kill 처리 방식을 명확히 한다.
- 새 패키지 설치, 패키지 버전 변경, ProjectSettings 변경은 별도 승인을 받는다.

## 5. 학생 프로젝트를 위한 설명 의무

구현 완료 보고는 결과만 나열하지 않는다. 게임 개발을 공부하는 학생이 이해할 수 있도록 다음을 반드시 설명한다.

- 요청을 어떤 구조로 나누어 구현했는지
- 주요 클래스, 메서드 및 데이터가 각각 어떤 역할을 하는지
- 실행 흐름과 Unity 생명주기에서 언제 동작하는지
- UniTask 또는 DOTween을 사용한 위치와 선택 이유
- 중요한 코드가 동작하는 원리
- 고려한 예외 상황과 실패 가능성
- 사용자가 Unity Editor에서 직접 확인하는 방법

코드를 대신 작성하는 데서 끝내지 말고, 사용자가 같은 방식을 다시 적용할 수 있을 정도로 설명한다. 다만 요청하지 않은 대규모 예제나 과도한 추상화는 추가하지 않는다.

## 6. 구현 및 검증 원칙

- 기존 스타일과 구조를 우선하며 요청과 무관한 리팩터링을 하지 않는다.
- 씬, 프리팹, ProjectSettings처럼 충돌 위험이 큰 파일은 승인 없이 수정하지 않는다.
- 가능한 범위에서 컴파일, 테스트 또는 Unity 검증을 수행한다.
- 검증하지 못한 항목은 완료로 단정하지 말고 이유와 수동 확인 방법을 남긴다.
- 오류를 숨기기 위한 빈 예외 처리나 임시 하드코딩을 하지 않는다.
- 비밀번호, 토큰, API 키, 개인정보를 코드나 진행 기록에 남기지 않는다.

## 7. Phase 기록 규칙

각 사용자 작업폴더는 다음 구조를 사용한다.

```text
Assets/
└─ _MemeberWorkspace/
   └─ <사용자 이름 또는 이니셜>/
      └─ _AgentLog/
         ├─ PROGRESS.md
         └─ phases/
            ├─ PHASE-001.md
            └─ PHASE-002.md
```

- 작업 시작 시 `PROGRESS.md`를 갱신해 승인된 계획과 현재 Phase를 기록한다.
- 각 Phase가 끝날 때 해당 `PHASE-NNN.md`를 작성하고 검증 결과까지 남긴다.
- Phase 번호는 기존 기록 다음 번호를 사용하며 과거 기록을 덮어쓰지 않는다.
- `PROGRESS.md`는 짧은 인덱스이자 재개 지점으로 유지한다. 긴 설명은 Phase 문서에 둔다.
- 새 채팅에서는 기록과 현재 사용자 폴더를 먼저 읽고, 완료된 조사를 불필요하게 반복하지 않는다.
- 기록과 실제 코드가 다르면 사용자에게 차이를 알리고 실제 상태를 확인한 뒤 기록을 정정한다.

## 8. 완료 보고 기준

완료 보고에는 다음을 포함한다.

1. 완료한 Phase와 결과
2. 생성·수정한 파일
3. 구현 방식에 대한 학습용 설명
4. 수행한 검증과 결과
5. 검증하지 못한 항목 또는 남은 위험
6. 다음 Phase가 있다면 진행 전 다시 필요한 승인

사용자 승인 없이 다음 Phase를 자동으로 시작하지 않는다.
